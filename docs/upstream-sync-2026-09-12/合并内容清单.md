## 1. 合并原则落地为判定标准

原则一「做上游的精简版，只合并高价值部分」→ 高价值判定（满足任一即入清单）：

| 级别 | 判定 | 说明 |
|---|---|---|
| ★★★ 必合 | 协议/格式正确性、计费正确、故障转移与可靠性、安全、依赖与工具链补丁 | 直接影响 fork 已发布版本（v1.x）的真实用户 |
| ★★ 选择性 | 增强既有子系统（护栏、缓存、仪表盘 UX）、小体积文档/测试 | 与 fork 精简目标不冲突时合并 |
| ★ 不合 | 跨切面的新子系统扩张、与 fork 定位无关的通用平台功能、纯演示/宣传物料 | 属"上游平台化"，与精简目标相悖 |

原则二「增强自有的特性功能」→ 每个主题额外标注它如何服务 fork 的四条自有产品线：
能力探测与确认（capability）、复杂度感知路由、定价时间窗覆写、供应商/模型上架开关 + 双语 UI。

### Q2b 全文取舍规则（2026-09-12 已裁决）

> 用户裁决：**上游译文只用于上游新增的 101 条，其他不变。**

合并后的 `zh-CN.json` 以上游 `zh-CN.json` 为骨架，译文取值分两类：

| 类型 | key 数 | 译文取值 |
|---|---|---|
| 上游独有 | 101 | **采用上游译文**（本次唯一采纳上游译文的部分） |
| fork 独有 | 119 | 保留 fork 现有译文 |
| 共有（逐字相同 792 / 不同 580） | 1372 | **一律保留 fork 现有译文**（含 580 条与上游译法不同的，不对齐上游写法） |

- **合并后规模**：`en.json` / `zh-CN.json` 各 **1592 key** = 119 + 101 + 1372（en 取双方 key 并集；zh-CN 按上表取值）
- **执行口径**：`zh-CN.json := 上游 zh-CN.json`，再把 fork `zh.json` 中**每一个存在的 key** 覆盖进去（覆盖范围 1372 + 119 = 1491）；`en.json := 双方 key 并集`（缺哪个补哪个）
- **副作用（已知并接受）**：上游后续修改英文文案时，若该 key 在 fork 保留集合内，需人工决定是否同步中文；`tests/i18n.test.js` 的 parity 用例只校 key 集合一致性，不校验译文内容

## 7. 执行机制方案（**已定：方案 A**）

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **A 全量合并 + 显式 revert 排除清单**（推荐） | 在 `sync/upstream-2026-09-12` 分支 merge 上游 main，再用独立 revert 提交剔除 §4 项；以后每轮同步照此办理 | 需维护一份排除清单；排除项被上游再次改动时产生针对性冲突（数量可控） | 上游 65 提交/6 天的节奏下，唯一可持续的机制；协议正确性自动跟进，历史可审计 |
| B 主题摘取（cherry-pick 主题包） | 只挑 T1–T4/T6 的提交区间打入 fork | 主题内部提交强依赖（如 #961 依赖 #945/#959 等），逐个摘取冲突量大且易漏；每轮重新做一遍 | 仅适合"一次性借鉴"，不适合长期跟车 |
| C 混合（本轮摘取 + 季度跟车窗口） | 本轮用 B 保持仓库最小，季度再做一次 A | 两套机制的维护成本叠加 | 备选 |

## 8. 分批执行顺序与门禁（确认后按序执行）

5. 批次④ 缓存 T4 + 仪表盘/多语言 T6（含 Q1/Q2 定稿）
6. 批次⑤ T5（依 Q3）+ T7 剩余 + 精简排除项
7. 批次⑥ 自有特性适配 F1–F7 + 13 冲突解法 + 三件套文档同步
8. 门禁：`make build` / `make test` / 仪表盘 `npm test`（含 i18n parity）/ 冒烟：启动网关+仪表盘，验证 /v1/models、能力探测页、定价时间窗编辑、供应商上架开关、双语切换

### 10.2 每轮同步的标准作业（Q5=A 制度化）

1. `git fetch upstream main` → 记录 `rev-list --count origin/main..upstream/main` 与本轮 merge-base
2. 建 `sync/upstream-<日期>` 分支，先打回滚 tag（`rollback/pre-upstream-sync-<日期>`）并推送
3. 试合并（worktree 内 `git merge --no-commit`）→ 记录冲突文件与 hunk 数
4. 全量合并；随后按 §4 排除清单实施文件级 revert（禁止整提交 revert）
5. 协议/供应商/可靠性批次优先跑门禁；再处理仪表盘与 i18n
6. 门禁：`make build` / `make test`（已知基线失败：`tests/perf`）/ 仪表盘 `npm test` + i18n parity
7. 回归 fork 六项自有特性（能力探测确认、能力图标、复杂度路由、时间窗定价、供应商双开关、分组折叠）
8. 通过后合并回 main 并打 tag；失败 `git reset --hard rollback/pre-upstream-sync-<日期>`
9. 每轮结束时更新本文档 §2/§4（新增上游提交的价值判定与排除项）
