## 6. 做得好 / 做得不够（诚实评估）

**做得好**

1. **先立规范文档再动手**，并把执行记录写回同一份文档（§8/§11–§17）——事后任何人可复核每一步的证据与判伪点，不依赖对话记录。
2. **不满足于单测**：6 项自有特性全部做了接口级实测（真二进制 + mock 上游 + 仪表盘同款 API），且每组都设了**判伪点**（3.0 vs 30.0、命中/不命中、绕行/不绕行、fail-open/部分过滤）——单侧通过说明不了任何事。
3. **"发布物 = 已验证物"做了等价证明**：发布提交与已实测提交的 diff 只有文档。
4. 边界诚实：媒体计费（上游 #970）只到单测级、helm 未并、`tests/perf` 既存失败，都写明而非含糊。

**做得不够**

1. **F2 首轮 9/10 是自找的**：断言"全池不可用"前没先算清健康标记的代数（10 分钟窗口内 ≥3 错且错误率 ≥50%）——只把 1 个目标推到达标，观测到的其实是"部分过滤"，差点误判成代码问题。
2. **A1 靠猜端点**跑了一轮空（`/admin/config` → 实为 `/admin/runtime/config`）。应先 `grep routes.go` 再写断言。
3. **跨端一致性靠事后逐项核对**：i18n key 集合、术语用词、前后端"显示 vs 计费"口径，目前都没有自动校验，全靠人眼。这类问题本次抓出 3 个（#3/#4/#7），下次还会再犯。
4. 时间窗定价的**前端**缺口是"写代码时漏了"而非"测出来"——说明合并时的规格核对（设计文档逐条比对）应该前置到实现阶段。

## 7. 可复用教训（已落库）

**技能 `gomodel-feature-delivery` §10（本次 +6 条）**

1. 选择类功能的观测法：mock 上游**逐次尝试日志** + 虚拟模型 `failover:false` + `session_affinity:false`，否则观测到的是重试兜底或会话钉住，会把"选错了+兜回"误判成"选对了"。
2. 阈值类断言先算代数、让**每个**对象各自达标（否则测的是"部分过滤"）。
3. 标着"需真实供应商凭据"的实测，先用 mock 上游即可完成。
4. 多个开关共用"不可用"表象时必须分开断言并记录对外表达差异。
5. 窗口/阈值/条件类语义必须做**两侧对照**（命中 + 不命中）。
6. 同一份数据前后端各有一套合并逻辑时，核对"显示口径 vs 计费口径"。

**流程教训（本次新增）**

7. 发布前用 `git diff --stat <已实测提交> <发布提交>` 证明"发布物 = 已验证物"。
8. `--ff-only` 合入时，"一次并入"的边界由**分支内已有的合并提交**承担，不需要为了好看再造一个空合并提交。

**mnemon**：F4 定性 + 实测配方与判伪点；双开关实测结论与状态码差异；`providers` 是 **map** 不是 list、策略清单读 `/admin/runtime/config`；v1.2.0 发布记录。
