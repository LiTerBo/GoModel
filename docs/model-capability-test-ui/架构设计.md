## 1. 现状（as-is）

### 1.1 后端探测管线

```
操作员点击按钮
  │
  POST /admin/models/test (同步)
  │
  ModelTestService.Probe(provider, model, probes)
    ├─ probeChat()              → verdict pass / inconclusive
    ├─ probeEmbeddings()        → verdict pass / inconclusive
    └─ probeFunctionCalling()   → verdict pass / inconclusive
  │
  返回 []Result{probe, verdict, detail, latency_ms, at}
  结果存 admin.handler.modelTestResults（内存 *modelTestStore）
```

- 结果不落库，仅内存回放（`GET /admin/models/test-results`）
- `ConfirmModelCapabilities` 调用 `registry.MergeModelCapabilities` 写入 `configMetadataOverrides`（内存 map）

### 1.2 能力来源体系（已有，`model-capability-detection.md` 已实现）

```
Layer 1: Remote registry (models.json)              → CapSrcRegistry
Layer 2: Provider self-reported metadata             → CapSrcDiscovered
Layer 3: Config.yaml metadata overrides              → CapSrcConfig
Layer 4: ID-based heuristic (InferCapabilitiesFromID)→ CapSrcHeuristic
Layer 5: Operator-confirmed test probes              → CapSrcTest     ← 本次要持久化
Layer 6: Audit-log observed sessions                 → CapSrcObserved ← 本次要持久化
```

各层通过 `MergeMetadata` 的 key-by-key 覆盖合并，最终 `Model.Metadata.Capabilities` + `CapabilitySources` 决定路由行为。

```
ModelRow.svelte
├─ 模型名称
├─ category columns（按类别显示价格信息）
├─ 能力徽标（"实测验证"/"流量验证"/WARN badge）

```

### 1.4 持久化先例 — pricingoverrides

`internal/pricingoverrides/` 的架构：

```
factory.go: New(ctx, cfg, storage, catalog, base)
  ├─ createStore() → storage.ResolveSQLBackend(SQLStore, MongoDBStore)

  │    └─ Refresh(ctx)  ← 启动时加载（从 SQLite List() → buildSnapshot）
```

接线点：`internal/app/init_catalog.go:117` `pricingoverrides.New(...)`，在 registry 初始化后执行。

### 1.5 确认路径现状

```
PUT /admin/models/capabilities
  ConfirmModelCapabilities(handler_modeltest.go)
    → registry.MergeModelCapabilities(provider, model, caps, CapSrcTest)
      → r.configMetadataOverrides[provider][model] = metadata  (内存 map)
      → r.enrichModelsLocked()  (内存 re-merge)
```

无持久化、无 SQLite、无回读。

## 2. 目标架构（to-be）

```
服务启动
  │
  ├─ registry 初始化（config.yaml metadata_overrides → configMetadataOverrides）
  │
  ├─ capability.New(ctx, cfg, app.storage, registry)   ← 新增
  │     ├─ createStore() → SQLStore (capability_confirmations 表)
  │     ├─ NewService(store, registry)
  │     │    └─ Refresh(ctx) → store.List() → 读所有持久化确认
  │     │    └─ 对每条记录: registry.MergeModelCapabilities(...) → 注入 configMetadataOverrides
  │     └─ StartBackgroundRefresh(interval) ← 可选，SQLite 无并发问题
  │
  ├─ admin handler 初始化
  │     └─ capability.Service 传递给 handler，用于 Confirm 路径
  │
  └─ 服务就绪

操作员在仪表板操作
  │
  点"运行能力测试"
  │  modelTest.runTest() → POST /admin/models/test → 面板显示结果
  │
  点"确认"
  │  modelTest.confirmCapabilities(provider, model, passedCaps)
  │    → PUT /admin/models/capabilities
  │      → capability.Service.Confirm(provider, model, caps, source="test")
  │         ├─ store.Upsert(ctx, confirmation)  ← SQLite 写
  │         └─ registry.MergeModelCapabilities(...)  ← 内存注入 + enrichModelsLocked()
  │
  │  面板关闭 → ModelRow 重渲染 → 图标高亮+✓
```

### 关键数据流

```
确认操作 ──→ 两写，顺序固定：
  1. store.Upsert(ctx, {
       provider, model, capability, source, value, confirmed_by, created_at
     })
     （失败则返回错误，不执行步骤 2）
  2. registry.MergeModelCapabilities(provider, model, caps, CapSrcTest)
     （内存操作，不会失败）
```

## 3. 模块详细设计

### 3.1 `internal/capability/` 包（新增）

独立包，模仿 `pricingoverrides` 的同构三层：

```
internal/capability/
├── store_sql.go      // SQLite store，capability_confirmations 表
├── store.go          // Store interface（方便后续 MongoDB 实现）
├── service.go        // Service: Refresh, Confirm, 后台刷新
├── factory.go        // New(ctx, appCfg, storage, registry) → (*Result, error)
└── factory_test.go   // 集成测试
```

#### 3.1.1 `store.go` — 接口

```go
type Confirmation struct {
    Provider    string `json:"provider"`
    Model       string `json:"model"`
    Capability  string `json:"capability"`    // "chat" | "embeddings" | "function_calling" | "vision"
    Source      string `json:"source"`         // "test" | "observed"
    Value       bool   `json:"value"`          // true=支持  false=确认不支持（预留）
    ConfirmedBy string `json:"confirmed_by,omitempty"`
    CreatedAt   int64  `json:"created_at"`
}

type Store interface {
    // Upsert inserts or replaces one capability confirmation.
    Upsert(ctx context.Context, c Confirmation) error
    // List returns all persisted confirmations.
    List(ctx context.Context) ([]Confirmation, error)
    // Delete removes a single capability confirmation.
    Delete(ctx context.Context, provider, model, capability string) error
    Close() error
}
```

#### 3.1.2 `store_sql.go` — SQLite 实现

```go
// 表结构
CREATE TABLE IF NOT EXISTS capability_confirmations (
    provider    TEXT NOT NULL,
    model       TEXT NOT NULL,
    capability  TEXT NOT NULL,
    source      TEXT NOT NULL DEFAULT 'test',
    value       INTEGER NOT NULL DEFAULT 1,
    confirmed_by TEXT,
    created_at  INTEGER NOT NULL,
    PRIMARY KEY (provider, model, capability)
);

// NewSQLStore(ctx, db) → *SQLStore
//   Upsert: INSERT OR REPLACE
//   List:   SELECT * FROM capability_confirmations ORDER BY provider, model, capability
//   Delete: DELETE FROM capability_confirmations WHERE provider=? AND model=? AND capability=?
```

#### 3.1.3 `service.go` — 业务逻辑

```go
type Service struct {
    store    Store
    registry ModelRegistry  // *providers.ModelRegistry 接口化
    mu       sync.RWMutex
    snapshot atomic.Value   // map[selector]map[capability]Confirmation（内存缓存）
}

func NewService(store Store, registry ModelRegistry) *Service

// Refresh 启动加载：store.List() → buildSnapshot() → registry.MergeModelCapabilities(每条)
func (s *Service) Refresh(ctx context.Context) error

// Confirm 确认能力：调用方（admin handler）提供已确认的能力集
// 对于每个能力 key 执行 store.Upsert +  registry.MergeModelCapabilities
func (s *Service) Confirm(ctx context.Context, provider, model string, caps map[string]bool, source string) error

// List 返回所有持久化确认记录（用于调试端点）
func (s *Service) List(ctx context.Context) ([]Confirmation, error)
```

`Refresh()` 的关键逻辑：

```
store.List() → [{provider, model, capability, source, value}, ...]
  → 按 provider/model 分组，每条调用 registry.MergeModelCapabilities(provider, model, {cap: value}, source)
  → Source 字段决定图标呈现：source=="test" 或 source=="observed" 均视为"实测"
```

#### 3.1.4 `factory.go` — 初始化

```go
func New(ctx context.Context, appCfg *config.Config, shared storage.Storage, registry ModelRegistry) (*Result, error) {
    store, err := createStore(ctx, shared)
    service, err := NewService(store, registry)
    if err := service.Refresh(ctx); err != nil {
        return nil, fmt.Errorf("capability refresh on startup: %w", err)
    }
    return &Result{Service: service, Store: store}, nil
}
```

#### 3.4.2 modelTest store 扩展

```javascript
// modelTest.svelte.js 新增
async confirm(provider, model) {
  const key = `${provider}/${model}`;
  const run = this.runs[key];
  if (!run?.results) return;
  
  // 收集 pass 的结果 → { capability: true }
  const caps = {};
  for (const r of run.results) {
    if (r.verdict === 'pass') {
      switch (r.probe) {
        case 'chat': caps.chat = true; break;
        case 'embeddings': caps.embeddings = true; break;
        case 'function_calling': caps.function_calling = true; break;
      }
    }
  }
  
  const result = await sendJSON("/admin/models/capabilities", "PUT", {
    provider, model, capabilities: caps
  });
  if (result.ok) {
    // 面板关闭，刷新模型列表刷新图标
    delete this.runs[key];
  }
  return result;
}
```

## 6. 关键设计决策

| AD | 决策 | 理由 | 实施状态 |
|----|------|------|----------|
| AD-1 | 能力确认走独立 `capability` 包，不直接改 registry 代码 | 与 pricingoverrides 同构，单一职责，便于测试 mock | ✅ 已实施（`internal/capability/`，commit A/B/C） |
| AD-2 | 两写顺序固定：SQLite 先 → registry 后 | SQLite 写是唯一可能失败的外部 I/O；registry 注入是内存操作、恒成功 | ✅ 已实施（`Service.Confirm`，`TestConfirmStoreErrorStopsBeforeRegistry` 钉住） |
| AD-3 | `capability_confirmations` 表存 `source` 字段 | 重启后必须能还原图标是「实测(test)」还是「流量验证(observed)」，否则图标态编码失效（D-6） | ✅ 已实施（`TestStoreSourceRoundTrip` + 重启回灌端到端） |
| AD-4 | `source` 不影响注入行为（test 和 observed 都调用 `MergeModelCapabilities`） | 两者对 registry 的语义相同（operator 确认的覆盖）；区别仅在前端渲染 | ✅ 已实施（handler 双端点均走 `confirmCapabilities`，仅 source 参数不同） |
| AD-5 | 启动加载放在 registry init 之后、admin init 之前 | 确保路由就绪前所有确认已注入；admin handler 初始化时可直接引用 service | ✅ 已实施（`init_capability.go`，挂在 `initPricing` 与 `initAdmin` 之间） |

## 附录：workflow 选项与遗留权衡

### 未包含在本轮的工作

1. **逐探测流式进度**（D-2）：当前保持同步阻塞；面板结构预留逐探测结果行，二期加 SSE 时只需把「一次性结果」换为「逐条推入」。
2. **流量验证（observed source）的持久化**：`PUT /admin/models/observed-capabilities` 同样走 `MergeModelCapabilities`，但未走 SQLite。本架构设计 `capability_confirmations` 表已预留 `source` 字段，observed 路径后续只需在同表 upsert，无需改表结构。
3. **配置热更新时的加载**：如果 operator 在运行时热更 config.yaml，registry 会 re-enrich，此时上次加载的持久化确认仍保留在 `configMetadataOverrides`（re-enrich 会重新 apply override 层但不会清空它），不需要额外处理。但如果 operator 修改了 config.yaml 的 `metadata_overrides` 覆盖了同一个能力的值，config override（层 3）比持久化确认（层 5）优先级高——但这是符合预期的：operator 声明应当优于实测结果，且重启后 config.yaml 的声明永远有效。
