# 模型能力测试 UI

> 基于 GoModel 现存探测管线（`internal/modeldata/modeltest`）与模型能力展示增强设计
> 日期：2026-09-09 ｜ 状态：✅ 已实施（A~G 全部完成，issue #15~#21 已关闭）

---

## 1. 业务目标与核心痛点

**目标**：为操作员提供一个「一眼了解 → 验证 → 确认 → 固化」的模型能力管理闭环，让能力探测结果真正影响路由决策，且重启不丢。

**痛点**：

1. **探测无反馈**：当前「运行能力测试」按钮仅显示「测试中…」→ 恢复「运行能力测试」，操作员不知测试进度、不知结果、原因为何。
2. **能力不可见**：模型是否支持 `function_calling`、`vision` 等路由关键能力，需要点进日志或看 API 文档才知道；"实测验证"/"流量验证"徽标仅模糊表示「测过」，未指明具体能力。
3. **确认无闭环**：探测结果（`pass`/`inconclusive`）返回后，需单独调 `PUT /admin/models/capabilities` 才能固化，但 UI 完全没有这个入口——结果算白测。
4. **重启即丢**：确认后写入 `ModelRegistry.configMetadataOverrides`（内存 `map`），进程重启蒸发。操作员需重测、重确认，与路由判型一致性冲突（详见 D-7）。

## 2. 存量事实基线

| 指标 | 数值 |
|------|------|
| 可探测能力数 | 3（chat / embeddings / function_calling），注册表另有 vision 等静态能力 |
| 单探测超时 | 30s（`tester.go` Config.Timeout） |
| 默认探测数 | 2（chat + function_calling，POST 支持自定义 probes 参数） |
| 总上下文超时 | 2min（`probeContext()` 上下文截止） |
| 现有持久化先例 | `pricingoverrides` SQLite store（`internal/pricingoverrides/store_sql.go`） |
| 能力来源种类 | 6 种（registry / discovered / config / heuristic / test / observed） |
| 当前前端结果利用 | `modelTest.svelte.js` `runs[key].results` 存储但从未渲染 |

## 3. 业务流程与设计思路

```
操作员浏览模型表
  │
  ├─ 每行模型名右侧显示能力图标
  │    ├─ 高亮+ ✓     = 实测确认 (source=test/observed)
  │    ├─ 描边半透明   = 静态声明 (registry/discovered/config/heuristic)
  │    └─ 不显示该图标 = 不支持
  │
  ├─ 点击"运行能力测试"（FlaskConical 图标）
  │     │
  │     行内展开面板
  │     ├─ [ running ] chat — 测试中…
  │     ├─ [ pass    ] function_calling — 200ms
  │     ├─ [ inconclusive ] embeddings — 上游未返回向量 (detail)
  │     └─ [确认能力] 按钮  ──→ 写入 SQLite + 更新图标
  │
  └─ 重启后：SQLite → 启动加载 → 注入 registry → 图标恢复
```

**核心原则**（D-5）：图标始终反映**路由实际生效的能力**（`ModelRegistry` 中的 `Capabilities` 与 `CapabilitySources`）。探测结果只展示在面板中，点击「确认」后才落库并更新图标。

### 状态迁移图

```
初始（注册表/推断）
  图标：描边（静态声明）
  │
  点"运行能力测试"
  │
  面板：逐 probe 显示 pass / inconclusive
  │
  点"确认"
  │
  ▼
  写入 SQLite   →  注入 registry configMetadataOverrides
  │                     │
  图标：高亮+✓         enrichModelsLocked() → 图标态更新（D-5）
```

## 4. 关键技术难点与解决

| 难点 | 描述 | 解决思路 |
|------|------|----------|
| **探测同步阻塞 vs 进度展示** | 当前 `POST /admin/models/test` 同步阻塞，前端只能知道 running/done 两态 | 保持同步（Q2=A），粗粒度状态 + 已耗时，逐探测流式留二期（面板结构预留逐探测行） |
| **确认后两写一致性** | 确认操作必须同时写 SQLite + 注入 registry，任一失败需回滚 | 先写 SQLite，失败直接返回错误；注入 registry 是内存操作不会失败，若两年后有持久化 registry 则加事务 |
| **启动回灌时机** | SQLite 持久化确认必须在 registry 初始化之后、路由对外服务之前加载 | 在 `init_catalog.go` registry init 完成后、admin handler 初始化前，新增 `capability.Load` 钩子注入 `configMetadataOverrides` |
| **图标状态数据源** | 图标需要综合 `Capabilities`（是否支持）和 `CapabilitySources`（来源）决定显示态 | 三级编码（D-6）：Capabilities[key]==true + source==test/observed → 高亮+✓；Capabilities[key]==true + source∈{registry/discovered/config/heuristic} → 描边；Capabilities[key]==false 或不存在 → 隐藏 |

## 5. 功能需求

- **FR-1 能力图标行**：每个模型行名称右侧显示一排能力图标，图标集合 = 文本生成、嵌入、函数调用、视觉（D-4），图标语义见 D-6。
- **FR-2 运行能力测试按钮**：保持现有 FlaskConical 按钮，双击或 hover title 可查看说明（测试目的、默认探测项）。
- **FR-3 行内展开结果面板**：点击按钮后，模型行下方展开面板，显示：
  - 粗粒度运行态（running / done / failed）及已耗时（D-2）
  - 逐 probe 结果行：probe 名称、verdict（pass/inconclusive）、latency、detail（inconclusive 原因）
  - 当所有 probe 完成时，显示「确认」按钮
- **FR-4 确认能力**：点击「确认」后：
  - 将本次通过（pass）的 probe 对应的能力（chat/function_calling/embeddings）写入 SQLite store，source=test
  - 调用 `registry.MergeModelCapabilities` 注入 configMetadataOverrides → `enrichModelsLocked()`
  - 关闭面板，更新图标状态
- **FR-5 重启加载**：服务启动时，从 SQLite 读取所有持久化能力确认记录，注入 `registry.configMetadataOverrides`，图标态自动恢复（D-7）。
- **FR-6 开关去文字**：`AccessToggle` 按钮去除 `<span>{rowToggleLabel}</span>`，保留 track+thumb 及 aria-label/title 无障碍语义。
- **FR-7 徽标整合**：图标行取代现有「实测验证 / 流量验证」两个徽标；「能力告警 WARN」徽标保留（WARN 是告警而非能力，功能独立）。

## 6. 非功能需求

- **NFR-1 单模型探测总时间**：≤2min（复用现有 `probeContext()` 上下文截止 + 单 probe 30s 超时）。
- **NFR-2 确认操作响应**：&lt;500ms（仅 SQLite 一次 write + 内存 enrich）。
- **NFR-3 持久化可靠性**：SQLite WAL 模式（与项目其他 store 一致），单表写入，无跨表事务要求。
- **NFR-4 启动开销**：SQLite 读取所有持久化记录 + 注入 registry，预期 &lt;10ms（记录数 ≤ 模型数 × 4 能力 ≈ 数百条量级）。

## 7. 数据模型

新增 SQLite 表 `capability_confirmations`（与定价覆盖 `pricingoverrides` 的 SQLite store 同构）：

```sql
CREATE TABLE capability_confirmations (
    provider    TEXT NOT NULL,
    model       TEXT NOT NULL,
    capability  TEXT NOT NULL,         -- "chat" | "embeddings" | "function_calling" | "vision"
    source      TEXT NOT NULL,         -- "test" | "observed"  （区分图标态，D-6）
    value       INTEGER NOT NULL,      -- 1=支持 0=确认不支持（仅 operator 确认的负例使用）
    confirmed_by TEXT,                 -- 可选：操作员标识
    created_at  INTEGER NOT NULL,      -- unix epoch ms
    PRIMARY KEY (provider, model, capability)
);
```

- `source` 字段是存的关键：重启加载时据此还原图标是「实测」（高亮+✓）还是「流量验证」（高亮+✓ 不同 tooltip）。
- `value=0` 记录 operator 确认的负例（`MergeModelCapabilities` 传 `false`），目前 UI 先不实现「确认不支持」的入口，仅后端预留。

## 8. API

### `PUT /admin/models/capabilities`（已存在，扩展行为）

现有端点，当前实现为 `ConfirmModelCapabilities` → `registry.MergeModelCapabilities(provider, model, caps, source=CapSrcTest)`。本次扩展：写入上述 SQLite store。

```json5
// 请求体（不变）
{
  "provider": "local-ollama",
  "model": "qwen-7b",
  "capabilities": { "chat": true, "function_calling": true }
}

// 响应（不变）
{ "ok": true }
```

新增读取端点：

### `GET /admin/models/capability-confirmations`（新增）

读取所有持久化的能力确认记录，用于前端启动时校验 / 启动日志。

```json5
// 响应
{
  "ok": true,
  "data": [
    { "provider": "local", "model": "qwen-7b", "capability": "function_calling",
      "source": "test", "value": true, "created_at": 1725800000000 }
  ]
}
```

## 9. 客户端能力边界

| 能力 | 范围 |
|------|------|
| 图标行 | 在模型表 `ModelRow.svelte` 内实现，不改变表格布局框架（category columns + actions 列结构不变） |
| 结果面板 | 行内展开（`<details>` 或折叠组件式），不弹 Modal、不跳转页面 |
| 探测进度 | 粗粒度 running/done/failed + elaped，不改变 `POST /admin/models/test` 同步语义 |
| 确认能力 | 通过 `modelTest` store 调用 `PUT /admin/models/capabilities`，不直接暴露 SQLite 写入口 |
| 视觉能力 | 图标映射仅含 4 个（文本生成/嵌入/函数调用/视觉），无探测的视觉能力只显示描边态 |
| 开关文字 | 仅去除 `AccessToggle` 中的文字 span，不改变按钮尺寸/交互逻辑/无障碍属性 |
| WARN 徽标 | 保持不动（能力告警功能独立于本次改动） |

## 10. 安全

- `PUT /admin/models/capabilities` 已受全局权限 middleware 保护（`global` scope），本次不改。
- 新端点 `GET /admin/models/capability-confirmations` 同级保护。

## 12. 差异总结（与参照实现 — pricingoverrides 对比）

| 维度 | 定价覆盖（pricingoverrides） | 能力确认（本次） | 差异 |
|------|---------|---------|------|
| 存储 | SQLite `pricing_overrides` 表 | SQLite `capability_confirmations` 表 | 独立表，结构不同 |
| 启动加载 | `service.Refresh(ctx)` 构建独立快照 | `service.Refresh()` + 注入 `registry.configMetadataOverrides` | 多一步回灌 registry |
| 后台刷新 | `StartBackgroundRefresh` 每分钟 | 同模式 | 一致 |
| 接线 | admin handler 直接调用 `Service.Upsert` | admin handler 调 `Service.Confirm` → 写 store + 注入 registry | 多一个两写步骤 |
| 关联性 | 独立 Service，无注入依赖 | 需 `registry` 引用 | 这是唯一架构差异（见架构设计 AD-1） |
