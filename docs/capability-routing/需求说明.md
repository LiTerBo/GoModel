## 1. 业务目标与核心痛点

**目标**：为 GoModel 建立「能力判定与动态路由体系」——让网关能（a）按任务复杂度自动升降模型档位、（b）按请求能力需求过滤候选模型、（c）对模型类型/能力做实测验证、（d）在运行时暴露判型错误。四者形成闭环，把「猜模型能力」升级为「验模型能力」。

**痛点**：

1. **静态判型无实测验证，推断不可靠**：GoModel 的模型类型/能力判定（`internal/modeldata/infer.go` 的 ID 启发式 + etc/models.json 注册表）从未对模型做实际验证。注册表只覆盖 20 个公开云厂商，本地/自命名模型（oMLX/vLLM/Ollama/LM Studio）只能靠 ID 启发式猜，默认判 `chat`——一个叫 `my-custom-model` 的 embedding 模型会被自信地判成 chat。**推断不一定正确，且没有任何机制发现它是错的。**

2. **能力检测结果不参与路由**：`infer.go` 已经算出了 `function_calling`/`vision` 等能力，但只被 dashboard 分类计数消费（`providers/registry_list.go` 的 `capabilityToCategory`/`modelMatchesCategory`）。一个带 `tools` 的请求可能被路由到不支持 `function_calling` 的模型，导致工具调用静默断链。

3. **无复杂度感知路由**：所有请求都走同一模型，无法按任务复杂度升降档。简单任务烧昂贵的 pro 模型、复杂任务又嫌 lite 不够用，成本与质量无法按需平衡。

4. **判型错误静默发生，无反馈**：运行时发生「类型错误/能力错误」（如把 embedding 模型当 chat 调、带 tools 的请求打到无工具模型）时，错误被当作普通上游失败处理，不记录、不提示，运维者无从感知判型有误。

## 3. 业务流程与设计思路

### 3.1 核心流程：四个工作流形成闭环

```
                    ┌──────────────────────────────────────┐
                    │   静态能力表（infer.go + CapabilitySources） │
                    └───────────────▲──────────────────────┘
                                    │ 校准（operator 门控确认后固化）
        ┌───────────────────────────┴───────────────────────┐
        │                                                   │
   W1 复杂度感知路由 ──消费──▶ 能力进路由                    │
   （ext.RouteSelector 扩展）    vision 硬过滤 + function_calling 软偏好
        │                                                   │
        │ 运行时判型出错                                       │
        ▼                                                   │
   W3 运行时错误检测 ──WARN 图标──▶ 提示 operator 触发验证 ──┤
                                    │                      │
              ┌─────────────────────┴──────────────┐       │
              ▼                                    ▼       │
   W2a 主动探测（手动，CapSrcTest）   W2b 被动观测（自动聚合，CapSrcObserved）──┘
```

### 3.2 工作流（四个，围绕静态能力表闭环）

| 工作流 | 职责 | 触发 | 落点 |
|--------|------|------|------|
| **W1 复杂度感知动态路由** | 复杂度估计 + 能力过滤 + 选 tier/target | 请求时（虚拟名 `smart` 或 adaptive 策略） | gateway / ext 扩展 |
| **W2a 主动探测** | 离线判型（type + function_calling） | **手动触发**（注册后提示，不自动跑） | modeldata / dashboard 模型模块 |
| **W2b 被动观测** | 审计日志挖掘（type + 能力，positive 证据为主） | 运行时自动聚合 | auditlog 轻量字段 + 聚合器 |
| **W3 运行时错误告警** | 类型/能力错误检测 → 记录 → WARN | 运行时 | 错误分类层 / dashboard |

### 3.3 模型判型流程（D1 + D5 定稿）

```
静态判型（infer.go + registry）
   → 模型验证（两条证据源，均需 operator 门控确认后才固化）：
        ├─ 主动探测（W2a，手动，CapSrcTest）
        └─ 被动观测（W2b，自动聚合，CapSrcObserved）
             ├─ ≥3 个不同会话观测到 tool_calls → 建议「支持」
             ├─ ≥3 个不同会话带 tools 请求上游报错 → 建议「不支持」
             └─ 其余（含成功但无 tool_calls）→ INCONCLUSIVE，不改判型
        └─ 确认 → 固化进 models.json / config override
```

**视觉系统**：模型模块需显式区分每条能力的来源——「静态判型」vs「主动探测」vs「被动观测」，让用户可感知哪条能力是被验证过的、由哪种方式验证。

## 4. 关键技术难点与解决

| 难点 | 描述 | 解决思路 |
|------|------|----------|
| 1. `RouteRequest` 无请求内容 | 复杂度估计需要 messages（代码块/多步列表/工具调用/当前消息长度），但 `Select(RouteRequest)` 拿不到请求体；`PrepareChatRequest` 手里有 `req.Messages` 却只把 `req.Model/Provider` 传入 resolution 链 | 扩展 `RouteRequest` 携带请求内容（messages/tools 摘要），穿透 resolver 接口边界（`inference_prepare.go` → `request_model_resolution.go` → `virtualmodels/resolve.go` → `adaptive.go`） |
| 2. 复杂度阈值不可照搬 | model-router 的 0.42/0.62/0.71 是 88 个 Hermes 会话 K-Means 标定的，GoModel 流量画像不同 | 试运行一个月用**人工经验值**；之后用**审计日志**采样重做 K-Means 校准 |
| 3. 能力过滤的默认极性 | `infer.go` 对本地/未知模型默认 `function_calling=false`，硬过滤会误杀「未标注但实际支持工具」的本地模型 | `vision` 硬过滤（判定可靠）+ `function_calling` 软偏好（有系统性歧义，operator 可 config 显式声明补救） |
| 4. 实测结果的权威性 | 探测「未命中」≠ 不支持（可能是探测 prompt 没触发工具调用，或模型恰好走文本路径） | positive 确认可补充；negative 不覆盖（INCONCLUSIVE 永不误杀静态判型已认定的能力） |
| 5. 探测成本与副作用 | 每模型一次真实 LLM 调用有 token 成本 + 云端模型误调用 | 手动触发为主 + 并发/预算控制；探测用最小载荷（max_tokens 极小） |
| 6. 被动观测的负面证据稀缺 | 不支持工具的模型通常「静默忽略 tools 参数」正常回文本，与「支持但选择不调工具」在观测上不可区分 | 负面判定仅认「上游显式报错」；「成功但无 tool_calls」一律 INCONCLUSIVE，避免误杀 |

## 5. 功能需求

### W1 复杂度感知动态路由

- **FR-1** 提供复杂度估计器：对请求 messages 计算复杂度分级（simple/medium/complex/very_complex），纯函数、无状态、可单测。
- **FR-2** 提供决策策略：复杂度 → tier 映射 → 选 target；支持配置每个 tier 的 primary/upgrade/fallback。
- **FR-3** 通过 `ext.RouteSelector` 扩展实现（独立 module，不进 core）；`Select` 返回空/越界时降级 round-robin（fail-open，复用现有 `adaptive.go` 的 panic 隔离语义）。
- **FR-4** 能力进路由：请求侧解析 `requires_function_calling`（`req.Tools` 非空）/ `requires_vision`（messages 含 `image_url` ContentPart）；候选侧从 catalog 拷贝能力；`vision` 硬过滤 + `function_calling` 软偏好。
- **FR-5** 阈值可配置，试运行期用人工经验值；预留审计日志重校准入口。

### W2a 主动探测（模型实测验证）

- **FR-6** 主动探测工具，入口在「模型」模块（dashboard Models 页），**必须手动触发**；支持「单模型 / 供应商全模型 / 全部模型」三种范围。
- **FR-7** 首期探测维度：**类型**（`type`：chat/embedding/image/audio/rerank，靠发对应 endpoint 探测响应）+ **function_calling**（发带 `tools` 的请求看是否回 `tool_calls`）。`vision/audio` 探测**记入待办**。
- **FR-8** 主动探测结果来源标注：新增 `CapSrcTest` 能力来源；dashboard 模型模块显式区分「静态判型」vs「主动探测」vs「被动观测」来源（视觉系统）。
- **FR-9** 主动探测结果固化：operator 确认后写入 models.json `capabilities` 字段 / config override；未确认仅展示。

### W2b 被动观测（审计日志挖掘）

- **FR-10** 审计日志新增轻量结构化信号字段（`had_tools` / `response_tool_calls` / `had_image`），不落请求/响应全文，按列可过滤。
- **FR-11** 被动观测自动聚合：≥3 个不同会话观测到 tool_calls → 建议「支持」；≥3 个不同会话带 tools 请求上游报错 → 建议「不支持」；其余（含成功但无 tool_calls）→ INCONCLUSIVE。建议经 operator 门控确认后才固化（`CapSrcObserved`）。

### W3 运行时错误告警

- **FR-12** 运行时检测「类型错误」（如 embedding 模型被当 chat 调、endpoint↔mode 不匹配）与「能力错误」（请求要求 function_calling/vision 但模型无法满足）。
- **FR-13** 类型/能力错误记录到审计日志，并在模型模块以 **WARN 图标**标识，提示 operator 触发模型验证。

## 6. 非功能需求

- **NFR-1** 路由决策延迟：复杂度估计 + 能力过滤在请求路径上为纯内存计算，开销 < 1ms（复用 Go 高吞吐路径，不做网络调用）。
- **NFR-2** 扩展隔离：selector 崩溃/超时不拖垮请求（沿用 `adaptive.go` 的 recover + fail-open 语义）。
- **NFR-3** 确定性：同一输入（模型清单 + config override + 规则版本）→ 同一判型结果，默认内存重算、不落盘（延续「能力检测确定性派生」决策）。
- **NFR-4** 实测探测默认不干扰生产流量：手动触发，探测请求限并发 + 最小载荷。
- **NFR-5** 向后兼容：未启用复杂度路由时行为不变；`smart` 虚拟名未配置时不影响现有模型解析。
- **NFR-6** 视觉区分不破坏现有 dashboard 分类计数。

## 7. 数据模型

```
# 能力来源枚举（core/types.go 现有，新增两项）
CapabilitySource: CapSrcRegistry | CapSrcDiscovered | CapSrcConfig | CapSrcHeuristic
                | CapSrcTest | CapSrcObserved

# 复杂度估计（新增）
ComplexityLevel: simple | medium | complex | very_complex
RouteDecision {
    session_id, source, complexity_level, complexity_score,
    selected_target, strategy, required_capabilities, ... }

# 主动探测结果（新增）
ModelTestResult {
    model_id, provider,
    test_type: type | function_calling,
    outcome: pass | inconclusive,          # 无 fail（negative 不覆盖）
    observed: { mode?, tool_call?, ... },
    tested_at, source: CapSrcTest }

# 被动观测信号（新增，审计日志轻量结构化字段，不落全文）
CapabilitySignal {
    had_tools: bool,           # 请求带 tools
    response_tool_calls: bool, # 响应含 tool_calls
    had_image: bool,           # 请求带 image_url
}

# 被动观测聚合建议（新增，经 operator 门控确认后固化）
CapabilitySuggestion {
    model_id, capability,
    verdict: support | unsupport,   # 仅此两种；INCONCLUSIVE 不生成建议
    evidence_sessions: int,         # 观测到该信号的去重会话数（阈值 ≥3）
    source: CapSrcObserved }

# 运行时错误信号（新增，落审计日志）
CapabilityErrorSignal {
    model_id, provider, session_id,
    error_kind: type_mismatch | capability_mismatch,
    required: capability, status_code, occurred_at }
```

## 9. 客户端能力边界

- **在 GoModel 内部实现**：复杂度估计、能力过滤、模型实测探测、运行时错误信号——全部在网关后端 + dashboard 完成。
- **不在本方案实现**：改变 OpenAI 兼容协议、新增客户端协议、agent harness 集成。
- **不改变**：`/v1/chat/completions`、`/v1/responses`、`/v1/embeddings` 等既有端点契约；现有 `virtualmodels` 的 redirect/failover/cost 策略语义。

---

## 10. 安全

- 模型测试触发走 `/admin/*`，沿用 master key / 托管 key 门禁，探测请求以被测试供应商的凭据发起，不引入新凭据面。
- 运行时错误信号只记录 model_id/provider/error_kind，**不落请求正文**（沿用审计日志脱敏纪律）。
- 探测请求走最小载荷（`max_tokens` 极小），避免误烧云端配额；不向第三方泄露 operator 配置。
